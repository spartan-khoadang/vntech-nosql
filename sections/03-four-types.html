Đây là bức tranh tổng thể, đi từ đơn giản nhất đến giàu quan hệ nhất.

Key-value: như một hash map khổng lồ — Redis, DynamoDB. [→] Document: mỗi bản ghi là một JSON — MongoDB, Firestore. [→] Wide-column: hàng có số cột thay đổi, chuyên ghi khối lượng lớn — Cassandra, HBase. [→] Graph: dữ liệu là node và cạnh, chuyên duyệt quan hệ — Neo4j.

Giờ mình đi vào từng loại.

(~1 phút)

3.1 · Key-Value

Đưa key, nhận value. Database không cần biết bên trong value là gì.

# key                     → value
session:8f3a             → {"userId":42,"exp":"18:00"}
cart:user:42             → [{"sku":"A1","qty":2}]
rate_limit:ip:1.2.3.4    → 17

# Redis
SET session:8f3a '{"userId":42}' EX 3600  # tự hết hạn
GET session:8f3a
INCR rate_limit:ip:1.2.3.4              # tăng nguyên tử
  • mạnh Đọc/ghi theo key O(1); nhiều hệ chạy in-memory → dưới 1 ms.
  • mạnh Dễ phân tán nhất: hash(key) là biết node nào giữ dữ liệu.
  • mạnh Có TTL: dữ liệu tự hết hạn, hợp với cache và session.
  • yếu Không hỏi được theo nội dung: "tìm mọi session của user 42" là không làm được nếu không tự tạo thêm key.
key-value

Loại đầu tiên và đơn giản nhất: key-value. Hình dung một cái hash map khổng lồ, phân tán trên nhiều máy. Mình đưa vào một key, nhận lại một value. Database không quan tâm value là chuỗi, JSON hay ảnh — với nó, value là một "hộp đen".

Ví dụ với Redis: SET một session kèm EX 3600 nghĩa là một tiếng sau nó tự biến mất. INCR tăng một bộ đếm một cách nguyên tử — dùng cho rate limiting.

Điểm mạnh: đọc ghi theo key là O(1), nhiều hệ chạy trong RAM nên dưới một mili-giây. Phân tán rất dễ vì chỉ cần hash key là biết node. [→] Có TTL cho dữ liệu tạm.

[→] Điểm yếu: không hỏi được theo nội dung. Muốn "tìm mọi session của user 42" thì phải tự tạo thêm key làm index.

Ví dụ shop online: giỏ hàng lưu theo key cart:user:42 — mở giỏ của user 42 thì cực nhanh. Nhưng hỏi "những giỏ nào đang có sản phẩm A1?" (để báo A1 sắp hết hàng) thì Redis chịu, phải mở từng giỏ ra xem. Muốn trả lời nhanh, app phải tự ghi thêm key product:A1:carts → [42, 57, …], và tự xoá khỏi đó khi user bỏ A1 ra khỏi giỏ.

(~2 phút)

3.2 · Document

Giống key-value, nhưng database hiểu cấu trúc bên trong value nên query và index được theo từng trường

{
  "_id": "p1001",
  "name": "Laptop X14",
  "price": 25990000,
  "category": "laptop",
  "specs": { "cpu": "i7", "ram_gb": 16 },
  "tags": ["ultrabook", "văn phòng"],
  "reviews": [ { "user": "an", "stars": 5 } ]
}
// laptop RAM ≥ 16GB, giá < 30 triệu
db.products.find({
  category: "laptop",
  "specs.ram_gb": { $gte: 16 },
  price: { $lt: 30000000 }
}).sort({ price: 1 })
  • mạnh Schema linh hoạt, khớp tự nhiên với object trong code.
  • mạnh Dữ liệu liên quan được lồng (embed) vào nhau → đọc một lần là đủ.
  • mạnh Có index phụ, aggregation, query theo trường lồng nhau.
  • yếu Quan hệ nhiều–nhiều phức tạp khó mô hình; document không được phình vô hạn (MongoDB giới hạn 16 MB).
document

Loại thứ hai: document. Về bản chất nó giống key-value — mỗi document có một _id — nhưng khác ở chỗ database hiểu cấu trúc bên trong. Document được nhóm vào collection, giống bảng nhưng không có schema cố định.

Đây là một laptop: có specs lồng bên trong, có mảng tags, có cả reviews. [→] Và mình query được thẳng vào trường lồng nhau: laptop có RAM từ 16GB, giá dưới 30 triệu, sắp xếp theo giá. Cũng đánh index được trên các trường đó.

Điểm mạnh: linh hoạt, thân thiện với lập trình viên, đọc một lần là có đủ dữ liệu.

[→] Điểm yếu: quan hệ nhiều–nhiều khó mô hình — slide sau có ví dụ; và một document không được phình vô hạn — MongoDB giới hạn 16 MB.

(~2 phút)

3.2 · Document · ví dụ

Đơn hàng ↔ sản phẩm là quan hệ nhiều–nhiều: nhúng vào đâu cũng có giá

Cách 1 · nhúng sản phẩm vào đơn
{ "_id": "order_9001",
  "items": [ { "sku": "A1",
    "name": "Áo thun",
    "price": 199000 } ] }

tốt Xem 1 đơn: đọc 1 document.

giá Đổi tên A1 → sửa hàng nghìn đơn đang chứa bản sao.

Cách 2 · nhúng đơn vào sản phẩm
{ "_id": "A1",
  "name": "Áo thun",
  "orders": [ "order_9001",
    "order_9002", … ] }

tốt Biết ngay A1 nằm trong đơn nào.

giá Bán chạy → mảng phình mãi, chạm giới hạn 16 MB.

Cách 3 · chỉ lưu id, tra sau
{ "_id": "order_9001",
  "items": [ { "sku": "A1",
    "qty": 2 } ] }
// + $lookup sang products

tốt Không lặp dữ liệu, không phình.

giá Lại phải JOIN — thứ document muốn tránh.

document · nhiều–nhiều

Ví dụ cho điểm yếu vừa rồi. Một đơn hàng có nhiều sản phẩm, một sản phẩm nằm trong nhiều đơn — quan hệ nhiều–nhiều. SQL chỉ cần thêm bảng nối order_items rồi JOIN, hỏi chiều nào cũng được. Document thì phải chọn: nhúng vào đâu?

Cách 1: nhúng sản phẩm vào đơn. Xem một đơn rất nhanh, nhưng đổi tên áo A1 thì phải sửa hàng nghìn đơn đang giữ bản sao.

[→] Cách 2: nhúng ngược, danh sách đơn vào sản phẩm. Sản phẩm bán chạy có hàng triệu đơn, mảng phình tới giới hạn 16 MB.

[→] Cách 3: chỉ lưu id rồi tra sau bằng $lookup. Gọn, nhưng đó lại chính là JOIN.

Quan hệ 1–nhiều thì document làm rất tốt — cứ nhúng con vào cha. Nhiều–nhiều thì không có "cha" rõ ràng, nên phải chọn theo câu query hay chạy nhất. Thực tế hay dùng cách 1 cho đơn hàng: giá và tên lúc mua vốn nên được giữ nguyên.

(~1,5 phút)

3.3 · Wide-column

Dữ liệu chia theo partition key, trong mỗi partition được sắp sẵn theo clustering key

CREATE TABLE view_history (
  user_id bigint, viewed_at timestamp,
  product_id text, device text,
  PRIMARY KEY ((user_id), viewed_at)
) WITH CLUSTERING ORDER BY (viewed_at DESC);

SELECT product_id FROM view_history
WHERE user_id = 42 LIMIT 20;   -- đọc đúng 1 partition
  • mạnh Ghi cực nhanh: ghi vào RAM + log, sau đó mới dồn xuống đĩa (LSM-tree).
  • mạnh Scale tuyến tính tới hàng trăm node; Cassandra không có master.
  • mạnh Chọn mức nhất quán theo từng query: ONE, QUORUM, ALL.
  • yếu Query bắt buộc đi theo partition key; không JOIN; thiết kế mỗi query một bảng.
  • đừng nhầm Khác columnar DB (ClickHouse, BigQuery) dùng cho phân tích.
wide-column

Loại thứ ba: wide-column, tiêu biểu là Cassandra. Cách nghĩ: dữ liệu được chia theo partition key — ở đây là user_id. Bên trong mỗi partition, các hàng được sắp xếp sẵn theo clustering key — ở đây là thời gian xem, mới nhất ở trên.

[→] Nên câu "20 sản phẩm user 42 xem gần nhất" chỉ cần đọc đúng một partition, dữ liệu đã nằm theo thứ tự — rất nhanh.

Điểm mạnh lớn nhất là ghi cực nhanh: nó ghi vào RAM và commit log trước, sau đó mới dồn xuống đĩa thành các file bất biến — cấu trúc này gọi là LSM-tree. Cassandra không có master, mọi node ngang hàng, scale gần như tuyến tính. Và mình chọn được mức nhất quán cho từng query: ONE là chỉ cần một máy trả lời, QUORUM là đa số, ALL là tất cả — càng nhiều máy thì càng chắc có dữ liệu mới nhất, nhưng càng chậm.

[→] Điểm yếu: query bắt buộc phải theo partition key, không JOIN, nên thường mỗi query thiết kế một bảng riêng. Và lưu ý đừng nhầm với columnar database như ClickHouse — loại đó lưu theo cột để phân tích, là một chuyện khác.

(~2,5 phút)

3.4 · Graph

Quan hệ được lưu thẳng thành cạnh, không phải tính lại bằng JOIN mỗi lần đọc

// gợi ý: bạn bè của An đã mua gì?
MATCH (me:User {name:"An"})-[:FRIEND]->(f)-[:BOUGHT]->(p)
WHERE NOT (me)-[:BOUGHT]->(p)
RETURN p.name, count(f) AS soBan ORDER BY soBan DESC
  • mạnh Mỗi node trỏ thẳng tới hàng xóm → duyệt quan hệ nhanh, không phụ thuộc tổng kích thước dữ liệu.
  • mạnh Query theo mẫu đường đi: bạn của bạn, đường ngắn nhất, chuỗi giao dịch.
  • Trong SQL, mỗi bước "bạn của bạn" là thêm một JOIN; tới 4–5 bước thì chi phí tăng bùng nổ.
  • yếu Khó chia ra nhiều máy; không hợp với thống kê trên toàn bộ dữ liệu.
graph

Loại cuối: graph. Dữ liệu là node — An, Bình, Chi, sản phẩm — và cạnh có tên — FRIEND, BOUGHT. Điểm khác biệt: quan hệ được lưu thẳng, mỗi node trỏ trực tiếp tới hàng xóm, nên duyệt không phụ thuộc tổng kích thước dữ liệu.

[→] Query bằng Cypher của Neo4j đọc gần như vẽ hình: từ An, đi theo cạnh FRIEND tới bạn bè, rồi theo cạnh BOUGHT tới sản phẩm, loại những thứ An đã mua. Kết quả: Laptop X14 được cả Bình và Chi mua → gợi ý cho An.

[→] Trong SQL, mỗi bước "bạn của bạn" là thêm một self-JOIN; đến 4–5 bước thì rất chậm.

[→] Điểm yếu: đồ thị khó cắt ra nhiều máy, và không hợp với thống kê kiểu "tổng doanh thu theo tháng".

so sánh 4 loại

Gom lại thành một bảng. Không có loại nào thắng ở mọi cột: key-value scale dễ nhất nhưng không query được theo nội dung; graph mạnh nhất về quan hệ nhưng khó scale.

Dòng cuối là hình ảnh để dễ nhớ: key-value là tủ đồ có số — biết số tủ thì lấy ngay. Document là tập hồ sơ — mỗi hồ sơ một kiểu, lục được theo nội dung. Wide-column là sổ nhật ký theo từng người — ghi liên tục, đọc theo thứ tự thời gian. Graph là sơ đồ mạng quan hệ.

(~1,5 phút)

Bốn loại trong một hệ thống

Hệ thống thật thường kết hợp nhiều loại, mỗi loại cho đúng phần dữ liệu của nó

Polyglot persistence: Redis cho session, MongoDB cho catalog, Neo4j cho gợi ý, Cassandra cho lịch sử. Chi tiết use case ở Phần 2. Mở toàn màn hình ↗
polyglot persistence

Trong thực tế, một hệ thống không chỉ dùng một loại. Đây là một shop online: Redis giữ session và giỏ hàng, MongoDB giữ catalog sản phẩm, Neo4j tính gợi ý, Cassandra ghi lịch sử xem và log. Phần thanh toán thường vẫn để ở SQL vì cần ACID.

Cách làm này gọi là polyglot persistence. Cái giá là phải vận hành nhiều hệ và đồng bộ dữ liệu giữa chúng. Đây cũng chính là phần mình sẽ đào sâu ở Phần 2: use case.
