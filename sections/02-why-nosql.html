Why NoSQL?

SQL vẫn rất tốt. NoSQL sinh ra để xử lý vài giới hạn cụ thể của nó: khó mở rộng ngang và schema cứng.

02 · why nosql

Phần hai, cũng là phần quan trọng nhất: đã có SQL rồi, sao còn cần NoSQL? Mình muốn nói rõ ngay từ đầu: SQL không hề lỗi thời. NoSQL ra đời để giải quyết vài giới hạn rất cụ thể. Mình sẽ đi qua hai vấn đề chính.

Vấn đề 1 · Mở rộng

SQL truyền thống mạnh lên bằng cách nâng một máy. NoSQL mạnh lên bằng cách thêm máy.

Scale up: có trần phần cứng và một điểm lỗi duy nhất. Scale out: chia dữ liệu theo shard key, mỗi phần có bản sao. Mở toàn màn hình ↗
scale up vs scale out

Vấn đề đầu tiên là mở rộng. Phía trên là cách truyền thống: scale up — mọi request vào một server database. Chậm thì mua thêm CPU, RAM, SSD. Cách này đơn giản, giữ ACID dễ, nhưng giá tăng rất nhanh, có trần phần cứng, và nếu máy đó chết thì cả hệ thống chết.

Phía dưới là scale out: dữ liệu được chia thành nhiều phần gọi là shard. Query router nhìn vào shard key — ví dụ key bắt đầu từ A đến H — để biết dữ liệu nằm ở máy nào. Mỗi shard lại có replica để nếu một máy chết thì vẫn còn bản sao. Tải tăng gấp đôi thì thêm máy.

(~2 phút)

Vì sao SQL khó scale ngang?

Khi dữ liệu nằm trên nhiều máy, JOIN và transaction phải chạy qua mạng

  • Trên một máy, JOIN và transaction rất rẻ. Trên nhiều máy, chúng phải phối hợp qua mạng.
  • Transaction trải nhiều máy cần two-phase commit: chậm, và một máy chậm làm cả giao dịch chờ.
  • cách NoSQL né Đặt dữ liệu hay được đọc cùng nhau vào một key / một document / một partition, để mỗi request chỉ chạm một máy.
vì sao sql khó scale ngang

Câu hỏi tự nhiên: sao không chia SQL ra nhiều máy luôn? Được, nhưng khó. Trên một máy, JOIN và transaction rất rẻ. Khi bảng orders ở máy 1 và users ở máy 2, một JOIN phải kéo dữ liệu qua mạng.

[→] Transaction cũng vậy: muốn đảm bảo "hoặc cả hai máy cùng ghi, hoặc không máy nào ghi" thì cần two-phase commit — chậm, và một máy chậm làm cả giao dịch chờ.

[→] NoSQL né vấn đề này bằng cách thiết kế để dữ liệu hay đọc cùng nhau nằm cùng một chỗ — cùng một key, một document hay một partition. Mỗi request chỉ chạm một máy, nên thêm máy là thêm sức chứa gần như tuyến tính.

(~1,5 phút)

Vấn đề 2 · Schema cứng & lệch mô hình

Code nghĩ bằng object lồng nhau, SQL bắt mình cắt chúng ra thành bảng phẳng

Trong code: một Order là một object
order = {
  id: 9001,
  customer: { name: "An", phone: "09…" },
  items: [
    { sku: "A1", qty: 2, price: 199000 },
    { sku: "B7", qty: 1, price: 25990000 }
  ],
  shipping: { city: "HCM", street: "…" }
}
Trong SQL: 4 bảng, cần ORM để ghép lại
orders(id, customer_id, shipping_id)
customers(id, name, phone)
order_items(order_id, sku, qty, price)
addresses(id, city, street)

-- thêm 1 trường mới cho đơn hàng:
ALTER TABLE orders ADD COLUMN gift_note TEXT;
-- trên bảng 500 triệu dòng…
  • impedance mismatch Độ lệch giữa object trong code và bảng trong DB. Document DB lưu thẳng object dưới dạng JSON, và thêm trường mới không cần migration lớn.
schema & impedance mismatch

Vấn đề thứ hai là schema cứng. Trong code, một đơn hàng là một object: có khách hàng, danh sách item, địa chỉ giao hàng — lồng vào nhau rất tự nhiên.

[→] Trong SQL, mình phải cắt nó ra bốn bảng, rồi dùng ORM để ghép lại mỗi lần đọc. Và khi sản phẩm cần thêm một trường như "lời nhắn quà tặng", phải ALTER TABLE trên bảng có thể hàng trăm triệu dòng — cần lên kế hoạch migration cẩn thận.

[→] Độ lệch này có tên là impedance mismatch. Document database lưu thẳng object dưới dạng JSON, nên khớp với code hơn, và thêm trường mới không cần migration lớn.

(~1,5 phút)

SQL vs NoSQL

Hai cách tiếp cận, mỗi bên mạnh ở chỗ bên kia phải đánh đổi

SQL (RDBMS)NoSQL
Mô hìnhBảng, hàng, cột, khóa ngoạiKey-value, document, wide-column, graph
SchemaCố định, khai báo trướcLinh hoạt, nằm trong code
Mở rộngChủ yếu theo chiều dọcChủ yếu theo chiều ngang
Giao dịchACID đầy đủ, nhiều bảngThường ACID trong 1 bản ghi / partition
Nhất quánMạnh (strong)Thường chọn được: mạnh hoặc "nhất quán dần"
Truy vấnSQL chuẩn, JOIN mạnh, ad-hoc tốtTối ưu cho các query biết trước
Thiết kếChuẩn hóa, tránh trùng lặpPhi chuẩn hóa, theo query
so sánh

Tóm lại thành một bảng. Mình chỉ nhấn mạnh ba dòng.

Mở rộng: SQL chủ yếu theo chiều dọc, NoSQL theo chiều ngang. Giao dịch: SQL có ACID đầy đủ trên nhiều bảng; NoSQL thường chỉ đảm bảo trong một bản ghi hoặc một partition. Truy vấn: SQL rất mạnh với câu hỏi bất chợt — ad-hoc — nhờ JOIN; NoSQL nhanh với các query đã biết trước lúc thiết kế, còn câu hỏi bất chợt thì thường chậm hoặc không làm được.

(~1,5 phút)

Điểm mấu chốt

NoSQL không tốt hơn SQL. Nó đánh đổi.

  • bỏ bớt JOIN, transaction nhiều bảng, query ad-hoc, đôi khi cả nhất quán mạnh.
  • đổi lấy Scale ngang, latency thấp, luôn sẵn sàng, schema linh hoạt.
  • hệ quả Câu hỏi đúng không phải "SQL hay NoSQL?" mà là "dữ liệu này được đọc và ghi như thế nào?"
takeaway phần 2

Nếu chỉ nhớ một câu của phần này thì đó là: NoSQL không tốt hơn SQL — nó đánh đổi.

Nó bỏ bớt JOIN, transaction nhiều bảng, query ad-hoc, đôi khi cả nhất quán mạnh. [→] Để đổi lấy scale ngang, latency thấp, sẵn sàng cao và schema linh hoạt.

[→] Vì vậy câu hỏi đúng không phải "SQL hay NoSQL", mà là "dữ liệu này sẽ được đọc và ghi như thế nào". Và câu trả lời cho câu hỏi đó sẽ dẫn mình tới một trong bốn loại NoSQL ở phần tiếp theo.

(~1 phút)
